# Приложение: проверка на данных задания

Основной вариант решения и ход рассуждений находятся в [README](README.md). Здесь описан воспроизводимый пример для коротких фраз из SQL.

В исходных данных 117 кандидатов, 695 упоминаний и 541 уникальная нормализованная фраза. Полных резюме, периодов работы и сведений о проектах в SQL нет. Файл `data/domains.sql` сохранён без изменения; его SHA256: `7128e15c6ca1b6f392c799d8085c629c368ef38a7ca5d1b9f78d8c6cb1a761c5`. `data.py` читает значения как текст и разбирает их в списки, не выполняя SQL в базе. Схема таблицы в задании не дана, поэтому о типе столбца и загрузке в БД этот пример ничего не утверждает.

`cards.json` содержит 11 ручных карточек. `request.json` задаёт обязательный финтех и желательную интеграцию банковского ядра. `matcher.py` проверяет признаки внутри одной части фразы и возвращает подтверждение, необходимость просмотра, отсутствие информации или противоречие. Простые правила сохраняют возможную связь отрицания с перечислением; при неоднозначности результат отправляется на просмотр. Это эвристика, которая не заменяет синтаксический и смысловой разбор полного резюме.

`search.py` содержит поиск по символьным n-граммам и поиск по эмбеддингам фраз. В `experiment.py` они сравниваются с проверкой по карточке. В последнем варианте поисковый балл задаёт порядок только после подтверждения обязательных и желательных требований. Эксперимент проверяет карточки для всех строк; предложенный в основном ответе отбор кандидатов перед подробной проверкой здесь не реализован.

В `checks.json` 10 авторских сценариев и 34 оценки выбранных пар. nDCG@2 считается только среди размеченных кандидатов каждого сценария. Это проверка нескольких случаев, а не оценка полноты поиска по всей базе. Темы карточек и примеров пересекаются, поэтому результат нельзя считать независимым подтверждением качества на новых требованиях. Актуальные значения и выдача сохранены в [experiment.json](results/experiment.json) и [metrics.csv](results/metrics.csv).

Замер на 10 000 профилей повторяет исходные 117 записей. Он измеряет проверку карточек без извлечения резюме, построения векторного индекса и расчёта новых эмбеддингов. Искусственные фразы с отрицаниями и разными проектами используются отдельно в блокноте и тестах. Они не представлены как часть исходного SQL.

Для проверки извлечения, автоматического составления карточек и смыслового разбора спорных пар LLM не запускалась. Эти этапы предложены в основном ответе и требуют отдельной проверки на полных документах.

## Запуск

Нужен Python 3.12. Пример без модели и все тесты используют стандартную библиотеку:

```bash
python experiment.py --offline
python -m unittest discover -s tests -v
```

Для эмбеддингов и сборки выполненного блокнота на Windows:

```powershell
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python experiment.py
.venv/Scripts/python build_notebook.py
```

На Linux и macOS путь к Python будет `.venv/bin/python`. Модель работает локально на CPU. При первом запуске скачиваются открытые веса, около 235 МБ; платные API не используются. Готовый `solution.ipynb` можно прочитать без запуска. `experiment.py --offline` сохраняет результат без метода эмбеддингов, поэтому для восстановления полного сравнения нужно выполнить обычный запуск.

Модель: [multilingual MiniLM](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2). [Веса ONNX](https://huggingface.co/Qdrant/paraphrase-multilingual-MiniLM-L12-v2-onnx-Q), версия `faf4aa4225822f3bc6376869cb1164e8e3feedd0`. Хэш весов и версии основных пакетов записываются в результатах.
